Doogle — **Do the Google** — is a unified build, bus and management CLI for the Google
ecosystem (Cloud Run, Firebase, Workspace and Apps Script, AI Studio, Vertex AI, the Agent
Development Kit, and more). Those products overlap and their setup guides are scattered;
Doogle is a curated, opinionated **decision guide plus dry-run-first setup blueprints** for the
most common builder workflows. It is not a magic wrapper for every Google product; it goes
deep and reliable on a small set of patterns and makes adding more a one-folder pull request.

Works from AI coding agents like [Google Antigravity](https://antigravity.google/): see [AGENTS.md](AGENTS.md) and the [agent guide](docs/USING_WITH_AGENTS.md).

> **Status (1.2.0rc1).** This is a public release candidate. All five
> shipped blueprints are `syntax-checked` against recorded CLI versions; none have been run
> end-to-end against a live Google Cloud project yet. Linux is the well-tested platform;
> Windows and macOS are not fully verified. Invited reviewers: start with
> [docs/INTRODUCTION.md](docs/INTRODUCTION.md). Evidence: [docs/QUALITY_REPORT.md](docs/QUALITY_REPORT.md).

```text
$ doogle ask "add login and a database to my react web app"
Recommended: firebase-auth-mvp  (Firebase Auth MVP (Hosting + Authentication + Firestore))  [offline, confidence: high]
$ doogle explain firebase-auth-mvp        # when to use it, when NOT to, services, cost, freshness
$ doogle plan firebase-auth-mvp --var project_id=my-mvp-123            # dry run: nothing changes
$ doogle plan firebase-auth-mvp --var project_id=my-mvp-123 --apply --approve-high-risk
$ doogle teardown latest --apply --approve-high-risk                     # clean up
```

## Decision matrix

The full side-by-side comparison (best fit, cheaper alternatives, services, public endpoints,
high-risk and manual steps, tools, verification level) is generated from the blueprints into
[docs/DECISION_MATRIX.md](docs/DECISION_MATRIX.md), so it never drifts from what the CLI runs.

Not sure? `doogle ask "<your situation>"` scores your words against every blueprint offline.
Add `--ai` to also ask Gemini (optional); the AI can only pick from the catalog and never runs anything.

## Quickstart

Requires Python 3.10+. Cloud tools (`gcloud`, `firebase`, `clasp`) are only needed when you apply a blueprint.

Install it as a tool (recommended), straight from GitHub:

```bash
pipx install "git+https://github.com/rjohnn1/Doogle.git"      # or: pip install "git+https://github.com/rjohnn1/Doogle.git"
```

or work from a clone (needed to contribute blueprints):

```bash
git clone https://github.com/rjohnn1/Doogle.git doogle && cd doogle
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"          # add ,ai for optional Gemini routing: ".[ai,dev]"
```

Then, from any directory:

```bash
doogle doctor                    # read-only checks: Python, blueprints, tools, sign-in state
doogle list                      # every blueprint with its verification level and age
doogle ask "move my gemini prototype from ai studio to production"
doogle explain ai-studio-to-vertex
doogle plan ai-studio-to-vertex --var project_id=my-side-project-123   # use your own project ID
```

Project IDs are the lowercase ID shown by `gcloud projects list` (not the display name).
Anywhere the docs say `YOUR_PROJECT_ID`, substitute yours.

`list`, `explain`, `plan`, `ask` (offline), `doctor`, `history`, `docs`, `share` and `validate`
never touch the network or your cloud resources, and work without any Google CLI installed.

### Commands

| Command | What it does |
|---|---|
| `doogle list [--category C] [--stale]` | Browse blueprints with freshness; `--stale` shows ones not verified in 180 days (`--stale-days N`) |
| `doogle explain <id> [--guide]` | Trade-offs, anti-patterns, services, cost note, freshness, variables; `--guide` prints GUIDE.md |
| `doogle plan <id> --var k=v [--vars-file f.yaml]` | **Dry run**: resolved commands, risk tags, public flags, idempotency checks, verify checks, teardown |
| `doogle plan <id> ... --apply` | Execute after confirmation (`--yes` for scripts, `--approve-high-risk` for high-risk steps) |
| `doogle resume <run-id\|latest>` | Continue a failed or paused run, skipping steps that succeeded |
| `doogle teardown <run-id\|latest> [--apply]` | Show, then run, the teardown recorded for that run |
| `doogle history [run-id]` | Runs recorded in `.doogle/state.json` |
| `doogle ask "<goal>" [--ai]` | Route a goal to a blueprint |
| `doogle doctor` | Read-only environment diagnostics |
| `doogle docs [--check]` | Regenerate `docs/DECISION_MATRIX.md` and the gallery above (`--check` for CI) |
| `doogle share <id> [--repo-url URL]` | Print a "Built with a Doogle blueprint" badge and blurb for your project's README |
| `doogle validate [--blueprints-dir D]` | Strict schema check (CI uses this) |

Every command accepts `--json`. Exit codes: `0` ok, `1` runtime failure or
out-of-date docs, `2` invalid input or blueprint, `3` blocked by a safety gate (nothing ran).

## Safety rules

1. **Dry-run is the default.** `plan` only prints. Nothing mutates without `--apply`.
2. **Explicit approval.** `--apply` asks you to type the blueprint id. Non-interactive sessions must pass `--yes`, or Doogle refuses.
3. **High-risk steps are blocked** (IAM changes, public endpoints, deletes) unless you also pass `--approve-high-risk`. This applies to `apply`, `resume` and `teardown`.
4. **Tools are checked up front.** If a required CLI is missing, Doogle refuses before step 1.
5. **No shell, ever.** Templates are tokenised before variables are substituted, so a value always becomes exactly one argument. Values are pattern-checked, cannot start with `-`, cannot contain newlines, and any unresolved `{{placeholder}}` is an error. Displayed commands are shell-quoted.
6. **Idempotent where possible.** Steps can declare a read-only `skip_if` check, so re-running on a project that already has the resource does not fail.
7. **Verified, not assumed.** Steps declare a read-only `verify_command` plus expected output; exit code 0 alone is not success. `verify_command` and `skip_if` are checked to be read-only (no create/delete/deploy/enable words, no curl uploads or method changes).
8. **Teardown only removes what this run created.** Every automated teardown entry declares `undoes: [step ids]`; if those steps were skipped because the resource already existed, or never ran, the entry is skipped (`doogle teardown` shows `WILL SKIP` and why).
9. **The state file is not trusted.** `resume` re-renders every command from the blueprint and refuses if `.doogle/state.json` differs; `teardown` refuses recorded commands that use a tool outside the allow-list or a never-automated pattern. The file is written atomically, `0600` in a `0700` directory, under a lock, with a `.bak` copy.
10. **Everything is recorded, secrets are not.** Each run records step statuses, timestamps, exit codes, output tails, variables and the rendered teardown. Output tails are redacted (API keys, OAuth tokens, JWTs, `Authorization` headers, `key=value` secrets, personal emails) before being printed or stored. `.doogle/` is git-ignored.
11. **Allow-listed tools only.** Blueprint commands may only call `gcloud`, `gsutil`, `bq`, `firebase`, `clasp`, `curl` (read-only) and `test`. The validator rejects secret-looking variables, exact price claims, shell operators and substitutions, interpreters, and never allows `gcloud projects delete`.
12. **Honest freshness.** Every blueprint states when and how it was last verified (`simulated`, `syntax-checked` or `live`) and against which CLI versions. `doogle list` and `explain` warn when that is more than 180 days old.

## Privacy: no telemetry

Doogle collects **no telemetry, analytics or crash reports**, and phones home to nobody.
Nothing leaves your machine except the commands you approve (which your own `gcloud`,
`firebase` or `clasp` sends to Google with your credentials), and, only if you opt in with
`doogle ask --ai`, your goal text plus the blueprint catalog sent to the Gemini API with your key.
Run state stays in `.doogle/` on your disk.

## Optional AI routing

```bash
pip install -e ".[ai]"
export GEMINI_API_KEY=...      # from Google AI Studio; never commit it
doogle ask --ai "I need a backend for a mobile app with a chat assistant"
```

Without a key, without the extra, or on any API error, Doogle falls back to offline routing and
says so. The default model is `gemini-4-hydrogen`, the current general-purpose generally-available
Gemini 4 model on the [Gemini API](https://ai.google.dev/gemini-api/docs/models) and
[Vertex AI](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/models/gemini/4-hydrogen).
Override it with `DOOGLE_GEMINI_MODEL`, and check those official model pages for newer stable IDs.

## For coding agents

Use `--json` everywhere, check exit codes, plan before apply, and never pass
`--approve-high-risk` without a human approving the exact plan. This works from a terminal
inside an AI coding IDE such as [Google Antigravity](https://antigravity.google/) (there is
no official Antigravity integration). Start with [AGENTS.md](AGENTS.md). See also
[docs/USING_WITH_AGENTS.md](docs/USING_WITH_AGENTS.md) and
[OPERATING_GUIDE.md](OPERATING_GUIDE.md#3-driving-doogle-from-an-agent).
